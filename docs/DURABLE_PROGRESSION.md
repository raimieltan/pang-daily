# Durable social and content progression

Authenticated gameplay uses `POST /api/player/commands`. Every command identifies an action and stable content IDs; the authenticated principal selects the player. There is no player ID selector, final social value setter, arbitrary unlock grant, or reward amount in this API.

The player's wallet lock serializes commands. The transaction includes the gameplay fact, wallet transaction, social rule effects, consumed event sources, discovered opportunities, chapter markers, and command receipt. A failed write rolls everything back. The same request key returns the original receipt; a new key for an already completed source cannot apply progression or pay again. Conflicting race completion facts are rejected.

`social_introduce` opens an authored conversation and records introduction. `social_choice` submits dialogue/node/choice IDs. The server checks its stored conversation cursor, authored choice conditions, and consumed choices. Presentation receives the refreshed domain snapshot through `SocialStoragePort`/`ServerPersistence`; it imports no Prisma code. Rewards for jobs, race outcomes, paid repairs, inspections, and Marketplace purchases are generated from server-owned facts, not separate client social events.

NPC values, flags, milestones, favors, scene reputation and repeat counters, crew standing/invitations/membership, rival identity, and unlocks remain relational records. Social events have a per-player sequence, including multiple events committed in one transaction. Rival continuity is reconstructed from this ordered ledger; aggregate counts also come from durable race results. Crew standing remains independent and uses existing M3 rules (current content does not award crew points).

Jobs retain acceptance, current objective, cargo and elapsed simulation time, terminal outcome, and linked payout. Optional authored `cooldownSeconds` is enforced using the latest durable terminal timestamp; current jobs have no cooldown. Acceptance retries must retain their command key. A new acceptance key after a terminal run intentionally starts a new run, subject to favor/cooldown rules.

Race records retain player/vehicle ownership, content ID, rival identity, start/completion timestamps, ordered checkpoints, validated outcome/elapsed time, and linked reward transaction. Bootstrap includes recent results and best finish/finish-count/win summaries across all recorded results. An interrupted local simulation is settled as a DNF on runtime reload, with no reward. This remains single-player route/order/time validation; it does not claim M6 authoritative physics validation. Future authoritative validation can replace the completion validator while preserving result identities and reward links.

There was no previous Chapter 1 beat catalog. `game-core/progression/chapter.ts` now defines the initial sequence `meet_mang_boy → complete_first_job → meet_casey → finish_first_race`. Stored evidence can complete consecutive beats automatically, including actions performed earlier. `chapter_continue` validates the current beat and its gameplay requirement; completed beats are harmless retries. Completion records `chapter_2_access` as a content unlock, without introducing a Chapter 2 scene. New players start at `meet_mang_boy`; the migration initializes existing empty Chapter 1 rows.

Deploy the committed `20260927050000_progression` migration with the normal `yarn db:deploy` workflow. Existing schemas/IDs remain intact. Tests deploy migrations only to the isolated test database. Run `yarn test:api:integration`, `yarn test`, and `yarn typecheck` to verify.
