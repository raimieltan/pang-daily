# M3.5 persistence operations

## Deployment shape

Use one Render web service for the Next.js web app, one Render web service for the NestJS API, and one **paid** Render PostgreSQL 17 instance in the same region. The web server rewrites `/api/*` to the API's internal origin. Browser sessions use the web origin. Set the API's HTTP health check path to `/api/health`; `/api/health/live` proves the process responds, while `/api/health` returns 503 if the database or required schema version is unavailable. The API may have a public Render URL for its HTTP health check, but PostgreSQL uses its **internal** URL and should have no unnecessary external access. [Render private networking](https://render.com/docs/private-network) and [HTTP health checks](https://render.com/docs/health-checks) describe the platform behavior.

This is two application processes and one managed database, not a service mesh. Start with one API instance and `DB_POOL_MAX=5`. The Prisma `pg` adapter caps each instance's pool at that number. Reserve connections for the web-independent migration job and Render operations; before adding replicas, check `instances × DB_POOL_MAX` against the database limit. Use the direct internal database URL initially. If concurrency later requires Render PgBouncer, test the command transaction and migration paths against it first; migrations should retain a direct connection. [Render connection pooling](https://render.com/docs/postgresql-connection-pooling).

## Configuration and secrets

| Environment | Database | Configuration | Schema command |
| --- | --- | --- | --- |
| Development | `compose.yaml` `db`, localhost only | `apps/api/.env.example` copied to ignored `.env`; web uses `API_INTERNAL_ORIGIN` | `yarn db:migrate` for authored changes; `yarn db:deploy` to verify committed migrations |
| Test/CI | isolated `db-test`, tmpfs | `apps/api/.env.test.example`; `API_TEST_ENV_FILE` | `yarn test:persistence` creates and removes a unique empty `_test` database, migrating from zero |
| Staging | dedicated paid managed PostgreSQL | Render environment/secret storage; `NODE_ENV=production` | `yarn workspace @pang-daily/api db:deploy` in API pre-deploy |
| Production | separate paid managed PostgreSQL | Render environment/secret storage; `NODE_ENV=production` | same explicit pre-deploy command after backup gate |

API variables: `DATABASE_URL` (private internal URL), `SESSION_SECRET` (unique random value, at least 32 characters), `FRONTEND_ORIGINS` (exact web HTTPS origin), `API_PORT` (Render service port, e.g. `10000`), `NODE_ENV`, `DB_POOL_MAX` (default 5). Set web `API_INTERNAL_ORIGIN` to the API's private service origin. Keep `DATABASE_URL`, session secret and any backup credentials in Render environment/secret storage; never set them as `NEXT_PUBLIC_*`, commit them, paste them into tickets, or print them in logs. `.env*` files are ignored except safe examples. Rotate secrets through the hosting provider; session secret rotation signs players out.

## Deploy and migration sequence

1. Review the migration SQL and its data implications. For a destructive change, write an expand/migrate/contract sequence when old and new app versions may overlap. Identify data that cannot be recovered from code. Verify the current app can read the expanded schema and the new app can read existing rows.
2. Take a manual pre-migration Render database export from the Recovery page and wait until it finishes. For high-risk changes, restore it into staging and check representative player balances, owned parts and progression first. Record the export timestamp and schema version in the deploy record.
3. Deploy to staging. Build the API with `yarn workspace @pang-daily/api build`; run `yarn workspace @pang-daily/api db:deploy` as an explicit **pre-deploy command**; start with `yarn workspace @pang-daily/api start`. Check `/api/health` and a fresh account bootstrap. Build/deploy the web with `yarn build:web` and `yarn start`, setting `API_INTERNAL_ORIGIN` to the private API URL. The web service needs no database credential.
4. Repeat for production after staging verification. Deploy database-compatible API before web changes that send new command shapes. Do not run `prisma migrate dev`, `db push`, or `migrate reset` in staging/production. API startup connects and checks readiness; it does not migrate schema. Render runs pre-deploy before routing to a new instance; a failed migration must stop rollout for investigation. [Render Prisma deployment](https://render.com/docs/deploy-prisma-orm), [pre-deploy commands](https://render.com/docs/deploys).

Schema readiness currently requires `SchemaVersion.version = 5`. Change that check with a matching committed migration. A failed migration may leave an incomplete `_prisma_migrations` record: inspect it and the actual schema before using Prisma's resolve command. Never mark a migration applied solely to make startup green.

## Backups and recovery

Use paid Render Postgres so continuous point-in-time recovery is available. Render currently retains 3 days on Hobby workspaces or 7 days on Pro and above. Keep a **manual export before every production migration**; Render exports remain available for 7 days, so download a copy to restricted storage if the release needs longer retention. At this project stage, continuous PITR plus pre-migration exports is the backup policy; review it before storing data whose loss would exceed that window. Free database plans do not provide this safety net. [Render backup and recovery policy](https://render.com/docs/postgresql-backups).

To verify a restore without touching production, open the database Recovery page, select a time before the migration and restore to a **new** staging database instance. Point a staging API at that instance, apply only compatible app/schema versions, check `/api/health`, then compare representative player wallet ledger, vehicles, inventory, social and chapter state. Alternatively, download the manual export and use `pg_restore --format=directory --no-owner --no-privileges` into a new empty non-production database, following Render's documented archive extraction instructions. Never restore over an active production database for a trial.

Local restore exercise on 2026-09-27: a `pg_dump -Fc` archive of the Docker test database was restored with `pg_restore --no-owner` into a new `pang_daily_restore_check` database. Source and restore both had 7 migration records, 466 player profiles and 1078 ledger transactions. The verification database and temporary dump were then removed. This proves the local logical-backup procedure; the first staging deploy should also exercise Render's PITR workflow.

If a migration corrupts production data, stop writes by taking the API out of service. Record the incident timestamp, failing migration and a fresh backup of the damaged database for diagnosis. Restore a new database to the latest known-good point before the migration; verify player data with a compatible API in staging; switch production `DATABASE_URL` to the recovered instance and redeploy the compatible API/web release. Reconcile any accepted writes after the restore point from transaction/command receipts if possible, and tell players when data could not be recovered. A code rollback alone cannot reverse a destructive database change.

## Diagnosing a failed save

API stdout contains one JSON `api.request` event per response and a `persistence.command` event for validated gameplay commands. Search by the `X-Request-Id` response header or the UI's support reference. Command events contain actor ID, player ID, command type, known target ID, `idempotency` hit/miss, and committed/rolled-back outcome. They never serialize DTO bodies, session tokens, cookies, SQL, connection strings or exception messages. `api.request_failed` includes a safe database class and Prisma code. `persistence.bootstrap` records outcome and latency. Count failed command/bootstrap events and inspect latency distributions from these logs; no dedicated metrics service is required yet.

Check `/api/health/live` before `/api/health` to distinguish an API process from database/schema readiness. A 401 means the player should sign in again. A 400/404/409 domain refusal needs corrected input or current state; do not replay it automatically. For a network error or 503 with an unknown write outcome, keep the **same idempotency UUID** and retry; a new UUID can duplicate a purchase. If the command receipt exists but refresh failed, retry only bootstrap. `SAVE_VERSION_INCOMPATIBLE`, `PLAYER_STATE_INVALID`, or `PLAYER_STATE_INCOMPLETE` need a compatible client/schema or data repair; never reset that player automatically.

The full local/CI validation command is `yarn test:persistence` (Docker and Playwright Chromium required). It runs pure tests, API tests, a clean test-database migration and seed, PostgreSQL integration tests, then authenticated browser journeys against the API and web servers. The integration script accepts only the local Docker test endpoint on port 55433 with a `_test` database name, and creates a new database for each run. The browser runner uses free ports and a separate Next build directory so it can coexist with a developer server.
