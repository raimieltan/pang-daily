Goal

Introduce Pang Daily's first production-grade backend and database layer without disrupting the responsive local game runtime.

This milestone moves long-lived progression from browser-owned state into a durable, versioned, server-owned persistence model while preserving Babylon.js as the owner of frame-level simulation.

The result should be a stable foundation for Chapter 1 save/load, economy integrity, persistent social systems, garage/vehicle ownership, future marketplace generation, and M6 authoritative multiplayer.

Why this milestone exists

By the end of M3 the game has enough interconnected progression state that local-only persistence becomes a structural risk:

wallet and transaction history

owned vehicles and vehicle condition

installed parts and inventory

jobs and race results

NPC relationships

scene reputation

crew standing

rival history

unlocks

Chapter 1 progression

If this state remains spread across Zustand, browser storage, feature-specific save blobs, and runtime objects, later work will require a large migration and create multiple sources of truth.

M3.5 establishes one clear rule:

Runtime simulation is local. Persistent progression is server-owned.

Architecture boundary

Client / Babylon owns transient simulation

Do not persist or round-trip frame-level state such as:

vehicle transform every frame

wheel state

suspension compression

steering input

throttle input

RPM every frame

live traffic transforms

pedestrian transforms

camera state

transient collision impulses

animation state

Backend owns durable progression

The backend becomes authoritative for:

player profile

wallet balance

transaction ledger

vehicle ownership

vehicle persistent condition

owned and installed parts

inventory

jobs

race results

reputation

NPC relationships

rival state

crew standing and membership

location/content unlocks

Chapter 1 progression markers

migration/schema version

Shared game-core owns deterministic rules

Pure TypeScript domain calculations should live in shared code that can execute both client-side and server-side where useful.

Examples:

repair cost calculations

race rewards

reputation changes

part wear

fuel cost

job payouts

unlock conditions

The backend must not trust client-submitted final values when the server can derive them from validated inputs.

Primary deliverables

NestJS API application is fully integrated into the monorepo.

PostgreSQL is the durable source of truth for persistent player progression.

Prisma schema represents all M2/M3 persistence requirements with migration history.

Authentication/session identity exists even if the first implementation is intentionally minimal.

A player can load a persisted profile and continue from prior progress.

Economy mutations are transactional and auditable.

Cars, parts, inventory, relationships, reputation, crew state, jobs, races, and unlocks persist correctly.

Existing local save data can be migrated or intentionally reset through a defined migration path.

Client code accesses persistence through a defined repository/API adapter instead of feature code directly knowing storage details.

Automated tests cover persistence, transactions, idempotency, authorization, and migration-critical flows.

Logging and failure handling make save failures diagnosable.

The architecture is ready for M5 save/load and M6 server-authoritative race validation without another major persistence redesign.

Required design rules

1. No generic giant save_game JSON blob as the primary model

Structured relational state should be queryable and independently migratable.

JSON may be used for narrow versioned metadata when relational modeling adds no value, but not as an escape hatch for the full player state.

2. No client-authoritative money

The client may request an action, but should not send newBalance as truth.

Bad:

PATCH /wallet
{ "balance": 30000 }

Good:

POST /jobs/:jobId/complete
{ "completionToken": "..." }

The backend determines the payout and records the resulting transaction atomically.

3. Money changes require ledger entries

Every increase/decrease of player funds must create a Transaction record with:

amount

type/category

source/reference

timestamp

resulting or correlatable wallet state

The wallet cannot drift independently from transaction history.

4. Mutation endpoints must be idempotent where duplicate requests are plausible

Examples:

race completion

job completion

purchases

rewards

part installation

Retrying a request because of a network failure must not duplicate rewards or charges.

5. Persistence failures must never silently look successful

The player should not see a successful purchase/reward/save confirmation if the server transaction failed.

6. Feature code must not talk directly to Prisma

Prisma access belongs inside backend persistence/domain services.

7. Client features must not know database structure

The client consumes API/domain DTOs and a persistence adapter, not Prisma-shaped objects.

8. Save schema changes require migrations

Breaking save changes require an explicit migration plan and tests.

9. Local simulation remains responsive during API calls

Backend integration must not turn normal driving into request/response gameplay.

10. Single-player comes first, multiplayer-compatible ownership second

Do not implement full multiplayer here, but avoid patterns that would make authoritative validation impossible in M6.

Save/bootstrap contract

Define a deliberate bootstrap DTO for loading the playable session instead of making the client issue dozens of unrelated requests before the game can start.

Example shape:

type PlayerBootstrap = {
  profile: PlayerProfileDto
  economy: {
    balance: number
  }
  vehicles: VehicleDto[]
  inventory: InventoryItemDto[]
  social: {
    npcRelationships: NpcRelationshipDto[]
    reputation: ReputationDto
    crew: CrewStateDto[]
    rivals: RivalStateDto[]
  }
  progression: {
    jobs: JobProgressDto[]
    recentRaceResults: RaceResultDto[]
    unlockedLocations: string[]
    chapter: ChapterProgressDto
  }
  saveVersion: number
}

Avoid including transient world simulation state in this DTO.

Migration strategy

M3.5 must explicitly handle the transition from current local persistence.

At minimum define:

current local save version

server save version

what local data is migratable

what data is intentionally discarded

one-time import behavior if used

conflict behavior when both local and server state exist

rollback behavior if import fails

For development builds, a clean reset may be acceptable, but the behavior must be explicit and documented.

Security / integrity baseline

This is not a full anti-cheat milestone, but basic trust boundaries are mandatory.

The server must not blindly trust:

requested wallet balances

arbitrary reward amounts

arbitrary reputation changes

arbitrary unlocks

arbitrary ownership claims

client-provided race winner state where validation can be performed

At minimum:

authenticate the acting player

authorize resources by owner

validate DTOs

use database constraints

use server-side domain rules for meaningful mutations

record enough metadata to debug invalid/duplicate requests

Observability / failure handling

Required baseline:

structured request/error logging

database error logging without leaking secrets

correlation/request IDs for mutating operations

health/readiness endpoint

meaningful API error contracts

save failure UI state on the client

no swallowed persistence exceptions

Optional but desirable:

lightweight metrics for failed saves, duplicate idempotency hits, transaction failures, and bootstrap latency

Rollout strategy

Backend integration should be incremental.

Recommended order:

infrastructure + Prisma foundation

identity/player bootstrap

economy

vehicles/inventory

social state

jobs/races/progression

client persistence adapter

local-save migration

hardening, observability, E2E

During migration, allow a temporary compatibility adapter if necessary, but do not maintain two permanent sources of truth.

Explicit non-goals

Do not expand M3.5 into:

full multiplayer

full open-world server simulation

server-side physics

MMO architecture

realtime synchronization of every world entity

sophisticated anti-cheat

cloud infrastructure overengineering

production billing

public social accounts/friends system

global marketplace economy unless separately scoped

M3.5 should build the persistence backbone, not a live-service platform.

Epic acceptance criteria

M3.5 is complete only when all of the following are true:

NestJS API is part of the normal development stack.

PostgreSQL + Prisma migrations can create the database from zero.

Persistent player state has a defined relational schema.

The current player can be authenticated/identified reliably.

A new player can be initialized exactly once.

A returning player can load the complete required bootstrap state.

Wallet balance persists server-side.

Every money mutation creates an auditable transaction.

Duplicate retried economy/progression requests cannot duplicate rewards/charges.

Owned vehicles persist.

Vehicle condition persists.

Owned/installed parts persist.

Inventory persists.

Job progression persists.

Race results persist.

NPC relationships persist.

Scene reputation persists.

Crew standing/membership persists.

Rival state persists.

Unlocks/Chapter progression required by current content persist.

Resource ownership is enforced server-side.

Client code no longer treats browser storage as the canonical progression source.

Save/bootstrap has version metadata.

Current local-save transition behavior is documented and implemented.

Persistence/API errors surface clearly and do not silently lose progress.

Integration tests cover critical domain writes using PostgreSQL.

E2E test proves progress survives a full page reload/new session.

No frame-level driving simulation has been moved into the backend.

Architecture is compatible with later authoritative race validation in M6.

Exit condition

A player can start Pang Daily, load a server-persisted profile, earn/spend money, own and modify a car, progress jobs/races, change NPC/reputation/crew state, reload the application, and recover that state consistently without browser storage being the canonical source of truth.

After this milestone, M4/M5 content can build on durable progression rather than inventing new save mechanisms per feature.
